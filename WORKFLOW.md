# RunbookOS: implemented workflows

This is a code-level inventory as of 2026-09-16, not a claim that every exported n8n workflow is imported, active, or deployed. Each step cites the file and method or node that implements it.

## Runtime wiring

1. `docker-compose.yml` starts PostgreSQL 16, Redis 7.4, n8n 2.30.3, the Spring Boot `control-plane`, and Next.js `web`. PostgreSQL initializes a separate `n8n` database through `infra/docker/init-n8n-db.sh`; n8n waits for PostgreSQL health; the backend waits for PostgreSQL and Redis health.
2. `docker-compose.yml` sets `N8N_BASE_URL=http://n8n:5678` in the backend and `CONTROL_PLANE_URL=http://control-plane:8080` in n8n. `apps/web/src/lib/api.ts` sends browser requests to `NEXT_PUBLIC_API_URL` and server-side requests to `INTERNAL_API_URL`, with `credentials: "include"`.
3. Local Compose publishes ports 5432, 6379, 5678, 8080, and 3000. This is **not** the approved production n8n posture: the 2026-09-16 human decision in `DECISIONS.md` requires no public n8n domain.

## Signup, login, organization, and session refresh

1. `apps/web/src/app/register/page.tsx` `RegisterPage.submit()` validates name, a personal **or** work email, and a 12–128-character password via `apps/web/src/lib/registration.ts`, then calls `api.signup()` in `apps/web/src/lib/api.ts`. The API helper JSON-serializes the plain object once, omits bearer authorization for signup, and includes cookies.
2. `AuthController.signup()` in `services/control-plane/src/main/java/com/vaibhav/runbookos/security/AuthController.java` accepts `POST /api/auth/signup`; `SecurityConfig.securityFilterChain()` permits signup, login, and refresh without a session. `AuthService.signup()` normalizes the email, rejects duplicates, persists a BCrypt hash, records `USER_SIGNED_UP`, and calls `issue()`.
3. `AuthService.issue()` creates a random opaque refresh token, stores only its SHA-256 hash in `RefreshSession`, and asks `JwtService.issue()` for an HS256 access JWT. `AuthController.response()` returns the access token in JSON and the refresh token in an HttpOnly, SameSite=Strict cookie scoped to `/api/auth`, with `Secure` controlled by `REFRESH_COOKIE_SECURE`. `api.signup()` stores the access token in browser `sessionStorage`, then the register page navigates to `/onboarding`.
4. `apps/web/src/app/onboarding/page.tsx` `submit()` calls `api.createOrganization()` then `api.switchOrganization()`. `OrganizationService.create()` saves the organization and OWNER membership; `switchTo()` reloads membership through `TenantAccessService.require()` and issues a new JWT containing organization and role claims. The browser stores that JWT and enters the dashboard.
5. `apps/web/src/app/login/page.tsx` `handleSubmit()` calls `api.login()` without a bearer header, then `api.currentUser()` and routes to the dashboard or onboarding. `AuthService.login()` verifies the BCrypt password, chooses the first active membership returned by the repository, records success or failure, and calls `issue()` for a new JWT and refresh session.
6. On a 401 from an authenticated request, `request()` in `apps/web/src/lib/api.ts` calls `POST /api/auth/refresh` without a bearer header but with cookies, stores the replacement JWT, and retries the original request once. `AuthService.refresh()` looks up the stored token hash, revokes the old session, detects reuse of a revoked session, and issues a rotated session. `AuthController.logout()` revokes the matching session and clears the cookie.

## Tenant and role checks

1. `JwtAuthenticationFilter.doFilterInternal()` in `services/control-plane/src/main/java/com/vaibhav/runbookos/security/JwtAuthenticationFilter.java` verifies bearer JWTs through `JwtService.verify()` and puts the user/organization/role claims in the security context. `SecurityConfig.securityFilterChain()` requires authentication for other API routes, except health, docs, inbound webhooks, and internal workflow callbacks.
2. Controllers such as `IncidentController`, `ExecutionController`, `AiAnalysisController`, and `ApprovalController` pass the selected organization from `AuthenticatedUser` into services. `TenantAccessService.require()` reloads the active membership from PostgreSQL; the JWT role is a routing hint, not the authoritative role.
3. Each service applies the relevant role check and uses organization-scoped repository lookups. Examples: `ExecutionService.create()` permits OWNER/ADMIN/RESPONDER; `AiAnalysisService.configure()` permits OWNER/ADMIN; `ApprovalService.decide()` reloads the approver role and rejects elevated self-approval or a duplicate approver.

## Incident intake and demo launch

1. For inbound signals, `WebhookController.receive()` exposes `POST /api/webhooks/{organizationId}/{source}`. `WebhookService.accept()` checks payload size, delivery ID, nonce, a five-minute timestamp window, and `HmacSigner.verify()` over `timestamp.nonce.rawBody`; it rejects replay and sanitizes the JSON before `IncidentService.ingest()`.
2. `IncidentService.ingest()` deduplicates an external delivery ID, computes a service/error/title fingerprint, groups a matching open incident within 30 minutes or creates a new one, saves the signal, and audits incident creation/grouping.
3. For the guided demo, `apps/web/src/app/dashboard/getting-started/page.tsx` calls `api.launchDemo()`; `IncidentController.demo()` seeds demo runbooks, ingests a checkout regression signal, and calls `IncidentService.addDemoEvidence()` to save one deployment record and one service metric. `RunbookService.seedDemoRunbooks()` requires OWNER/ADMIN.
4. `IncidentController.detail()`/`IncidentService.detail()` return tenant-checked incident, evidence, and comments. `IncidentController.transition()`, `assign()`, and `comment()` use `IncidentService` role checks and audit state changes. `apps/web/src/app/dashboard/incidents/[id]/page.tsx` calls these operations and loads incident/analysis/postmortem views.

## Execution, outbox, n8n, and callback

1. The incident page's `IncidentDetailPage` calls `api.createExecution()` in `apps/web/src/lib/api.ts` with `workflowKey: "incident-triage"` and a random `Idempotency-Key` header. `ExecutionController.create()` exposes `POST /api/executions`.
2. `ExecutionService.create()` checks current tenant membership and role, requires an existing incident and idempotency key, then takes the named definition from `WorkflowRegistry.require()`. In one transaction it persists an execution, queued step rows, an `OutboxEvent` of type `WORKFLOW_DISPATCH`, an execution event, and an audit record. `retry()` and `retryStep()` also create outbox events. `ApprovalService.authorize()` creates an `APPROVAL_REQUESTED` outbox event only when Java policy requires approval.
3. `OutboxProcessor.process()` polls up to 20 PENDING events, claims each, and wraps delivery with a Resilience4j bulkhead, circuit breaker, and retry. `dispatch()` sends execution events to `POST /webhook/runbookos-execute`; `dispatchApproval()` sends approval events to `/webhook/runbookos-approval`. Both sign `timestamp.nonce.serializedBody` with `HmacSigner.sign()`. For executions, `ExecutionTokenService.issue()` adds a short-lived HMAC-signed token scoped to execution, organization, nonce, and allowed action IDs.
4. The exported `automation/n8n/workflows/runbookos-execute.v1.json` has a `Receive Signed Execution` webhook and `Verify Dispatch and Execution Token` Code node. That node checks HMAC and token signature/scope/expiry. It then sends signed `RUNNING`, per-step `SUCCEEDED`, and `SUCCEEDED` execution callbacks to the backend using `CONTROL_PLANE_URL` and acknowledges the webhook. **The per-step outputs are simulated Demo Mode results; this export does not run real diagnostics or a production remediation.**
5. `WorkflowCallbackController.callback()` receives `POST /api/internal/workflows/callbacks`. `WorkflowCallbackService.accept()` validates JSON, a two-minute timestamp window, HMAC, a persisted one-use nonce, execution token, organization-scoped execution, and allowed action ID before changing step/execution state and publishing timeline events. `ApprovalCallbackController.decide()` separately verifies HMAC, timestamp, and nonce before `ApprovalService.decide()` reloads membership and eligibility.
6. `apps/web/src/app/dashboard/executions/[id]/page.tsx` loads `api.execution()` and calls `authorizedStream()` for `/api/executions/{id}/events` so the timeline can update. Exported n8n workflows are all `active: false`; `automation/n8n/README.md` says they must be imported and activated for the webhook path to exist.

## AI analysis and evidence grounding

1. `AnalysisPanel` in `apps/web/src/components/analysis-panel.tsx` calls `api.analyze()`; `AiAnalysisController.analyze()` exposes `POST /api/incidents/{incidentId}/analyses`; `AiAnalysisService.analyze()` requires OWNER/ADMIN/RESPONDER and an incident in the selected organization.
2. `AiAnalysisService.analyze()` reads only the incident's stored `IncidentEvidence` rows (in collected-at order). `EvidenceGuard.guard()` recursively redacts sensitive keys and token-like strings, caps each string at 8,000 characters, and replaces text matching its embedded-instruction patterns. `AnalysisPrompt.render()` attaches incident title, severity, affected service, evidence IDs/kinds/titles/sanitized content, and an output-token ceiling.
3. If the organization is not in Demo Mode, `AiAnalysisService.analyze()` iterates **enabled organization provider configurations in ascending numeric priority**, not a fixed OpenAI→Anthropic→Gemini→Groq sequence. It skips an open per-provider failure circuit or an over-budget prompt, retries up to that config's `maxRetries`, and stops at the first successful output. `RemoteAiModelClient.analyze()` decrypts that config's key and calls its official API endpoint (or a validated public HTTPS compatible endpoint) with configured timeouts.
4. If Demo Mode is on, there is no remote call. If no remote config succeeds—or none is enabled—even a non-demo organization receives `DemoAiModelClient.analyze()` deterministic output. `AnalysisQualityValidator.validate()` rejects missing citations on non-hypotheses, references to IDs not in the incident evidence set, invalid confidence, empty recommendations, and a narrow SEV1 contradiction check. `AiAnalysisService.analyze()` persists output, quality metrics, provider/model/tokens/cost/fallback reason and audits completion or validation denial. AI output does not authorize actions.

## Policy and human approval

1. `ApprovalController.authorize()` calls `ApprovalService.authorize()`, which calls `PolicyEngine.decide()` for a specified incident, runbook version, step, environment, risk, and required role. `PolicyEngine.evaluate()` always denies PROHIBITED risk and HIGH_RISK in Demo Mode; default READ_ONLY is allowed, REVERSIBLE needs one approval, and HIGH_RISK needs two distinct eligible approvers with typed confirmation.
2. If policy requires approval, `ApprovalService.authorize()` persists a pending request and an approval-delivery outbox event. `ApprovalController` exposes inbox/detail/decisions; `ApprovalService.decide()` rechecks active membership, risk eligibility, pending/expiry state, duplicate approvers, self-approval, and phrase before saving a decision and auditing it.
3. `automation/n8n/workflows/approval-delivery.v1.json` has a signed approval webhook but calls Slack/email sub-workflows; `send-slack-notification.v1.json` and `send-email-notification.v1.json` currently return simulated notifications rather than deliver messages. The public web approval UI is a separate decision path.

## Audit append and hash computation

1. Services call `AuditService.record()`, `recordSuccess()`, or `recordDenied()` for signup/login, tenant denials, incident changes, analyses, policy decisions, approvals, execution intents, and other state/security events. `AuditService.record()` captures actor, organization when available, action/resource/outcome/reason, metadata, timestamp, and correlation ID. Its `REQUIRES_NEW` transaction lets denials survive a caller transaction rollback.
2. `AuditEvent` in `services/control-plane/src/main/java/com/vaibhav/runbookos/audit/AuditEvent.java` has no setters; database triggers reject update/delete. `V8__reliability_security_observability.sql` defines `chain_audit_event()`: for the same organization (including the null-organization bucket), select the latest `event_hash` by `occurred_at DESC, id DESC`; use 64 zeroes if absent; SHA-256 hash the concatenation of previous hash, event ID, action, resource type, resource ID or empty string, outcome, timestamp text, and JSON metadata text; store `previous_hash` and `event_hash` before insert.
3. `AuditController.list()` and `AuditService.findForOrganization()` provide tenant-scoped paginated audit reading. **No application method verifies an existing chain.** The migration backfill also assigns each pre-V8 row a zero previous hash rather than linking historical rows.

## Inconsistencies Found

1. **Outbox retry/dead-letter behavior diverges from documentation.** `docs/operations/reliability-observability.md` and README describe five exhausted deliveries becoming dead letters. Current `OutboxProcessor.process()` catches dispatch failures but only logs them; it does not call `OutboxEvent.failed()`. Since `claim()` leaves status `PROCESSING` and `OutboxEventRepository.findReady()` selects only PENDING, the failed event can become stuck indefinitely. `git log -p` shows the failure call was removed in commit `cc133cd`.
2. **The claimed audit integrity verification is absent.** README, `docs/operations/backup-restore.md`, and `docs/security/threat-model.md` describe hash-chained audit integrity and checking/restoring recent hashes; the code has the insert trigger in `V8__reliability_security_observability.sql` but no verifier. The backfill makes independent zero-root hashes for older rows. Concurrent inserts may also read the same predecessor without a per-tenant serialization lock; this risk has not been runtime-tested.
3. **Workflow exports do not equal running automation.** All 12 exported JSON workflows have `active: false`; no Compose startup step imports/activates them. README's architecture flow describes bounded evidence collection through n8n, but the `runbookos-execute.v1.json` gateway only reports simulated Demo Mode success for allowlisted step IDs. The other diagnostic sub-workflows return static Set-node evidence and are not connected to that gateway.
4. **Java policy is not on the visible execution-create path.** README and `docs/architecture/workflow-boundaries.md` state policy checks precede every executable action. `ExecutionService.create()` does tenant/role and workflow-name checks, but does not call `PolicyEngine.decide()` or `ApprovalService.authorize()`; the n8n demo gateway marks allowed IDs complete. This currently avoids real remediation because the gateway is simulated, but the stated invariant must be rechecked before adding real actions.
5. **n8n Basic Auth configuration is dead for the pinned image.** `docker-compose.yml` sets `N8N_BASIC_AUTH_ACTIVE/USER/PASSWORD`, but n8n 2.30.3 uses built-in user management rather than instance Basic Auth. The local unauthenticated editor shell returned 200, while `/rest/workflows` returned 401. The human decided to keep n8n private rather than add a proxy; see `DECISIONS.md`.
6. **The n8n execution signature check lacks timestamp/replay validation.** Unlike `approval-delivery.v1.json`, the `Verify Dispatch and Execution Token` node in `runbookos-execute.v1.json` checks HMAC but not timestamp age or dispatch nonce reuse. It also reconstructs the body with `JSON.stringify(input.body)` rather than verifying the exact raw bytes Java signed, so serialization differences could reject valid requests or weaken the intended exact-body contract. This is a code-path asymmetry, not proof of exploitation.
7. **Local example defaults are deliberately not production-ready.** `docker-compose.yml` contains example/default PostgreSQL password, JWT, encryption, HMAC, and n8n key values, while `application.yml` requires three platform secrets with no defaults. The previously approved Stage 2 gate remains necessary; no example values may be deployed.
8. **Forgot-password UI is a placeholder.** `apps/web/src/app/login/page.tsx` renders “Forgot password?” with `href="#"`; no password-reset request exists in `apps/web/src/lib/api.ts` or `AuthController`.
9. **Refresh-token reuse revocation may roll back.** `AuthService.refresh()` is `@Transactional`; after detecting a revoked token it calls `sessions.revokeAllForUser()` and then throws `AuthenticationDomainException`. Unless the revocation repository supplies its own independent transaction, the thrown runtime exception rolls back the revocations while `AuditService`'s separate `REQUIRES_NEW` audit entry survives. The intended “revoke all on reuse” security behavior therefore needs a transaction-boundary test and correction.
